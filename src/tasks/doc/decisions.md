# 关键决策记录

> 记录"为什么这么设计"以及"放弃了什么方案"。目的是三个月后还有人能看懂当时的取舍，不用重新推一遍。
>
> 每条格式：**结论 → 理由 → 放弃的方案 → 影响**

---

## D1. 新建 `src/tasks` 顶层目录

**结论**：任务编排层独立成 `src/tasks`，与 `core`、`start` 平级。

**理由**
- `src/core/agx_xarm_pick` 已经把"能力 + 任务流程 + 调试工具 + 假数据"混在一个包里（`demo_pick.cpp` 甚至直接带着任务参数 `lift_height`/`retreat_distance`）
- `src/core/agx_xarm_smach` 是 2021 年的 SMACH 任务原型，硬编码了别的机器上的路径（`/home/agx/catkin_workspace/...`），`node.py` 没被安装，跑不起来——它是重写对象，不是可复用的基础
- 依赖方向干净：目前**没有任何包依赖 `agx_xarm_pick`**，是抽层的窗口期

**放弃的方案**
- `src/core/tasks/`：不新增顶层，但任务与能力仍在同一个顶层组里，将来 `core` 单独交付会带上任务
- `src/start/tasks/`：`start` 的语义是"把硬件跑起来"（bringup/驱动/UI），放任务逻辑会让它变成三种语义混装；而且 `start/lifting_ws` 是内嵌子工作空间，再混进任务包容易分不清

**影响**：加新任务不碰 `core`、`start`。

## D2. 任务层用 C++

**结论**：C++，不用 Python。

**理由**：能力层最难的机械臂逻辑（`AgxXarmPick`、MoveIt 用法）已经是 C++。用 Python 要么加跨语言桥，要么把抓取逻辑重写一遍。任务代码本身是"顺序 + 调服务"，C++ 的啰嗦可以接受。

**放弃的方案**：Python + `moveit_commander`（迭代快，但要跨语言或重写）

**影响**：改参数要 `catkin_make`；换来的是单一语言、能直接复用现有类。

---

## D3. 任务契约用 actionlib

**结论**：`/agx_task/run` 用 actionlib，不用 service + 自定义 topic。

**理由**：任务要跑几十秒到几分钟，必须能取消、能知道卡在哪一步。手写这套东西就是现在代码里 `order.cpp` 伪造 `/move_base/result` 假装导航到达的来历。actionlib 原生提供 goal / feedback / cancel / result。

**放弃的方案**：`RunTask.srv` + `TaskState` 话题 + `CancelTask.srv`（更贴近现有代码风格，但要自己维护状态机）

**影响**：Runner 用 `SimpleActionServer`，长任务在 worker 线程跑，goal 回调立刻返回。

---

## D4. `run()` 阻塞，Runner 开线程

**结论**：`TaskBase::run()` 允许阻塞，由 Runner 在单独线程执行。

**理由**：任务代码写成从上到下的直线（"等升降稳定 → 规划 → 移动"），好读好改。非阻塞要求任务自己写状态机/回调，复杂度不成比例。

**放弃的方案**：非阻塞 `run()` + 任务内部状态机

**影响**：取消靠 `ctx.canceled()` 轮询 + 能力对象内部的取消标志；`ctx.sleep()` 要可被取消打断。

---

## D5. `capability_arm` 用细粒度

**结论**：暴露 `moveToPose` / `moveLinear` / `moveToNamed`，不用粗粒度的 `pick()` / `place()`。

**理由**：当前任务（`arm_move_to_pose`）是"移动到指定位姿"，**不抓东西**。粗粒度的 `PickAction()` 内含 AR 码编号、HOME 位姿、接近距离等硬编码，用不上还会被绑住。

**放弃的方案**
- 只用粗粒度：一两天能跑，但每个新任务都要改 `agx_xarm_pick`
- 完全重写抓取逻辑：工作量和风险都不必要，本任务不需要抓取

**影响**：实现时把 `agx_xarm_pick` 里 `MoveToA`（`agx_xarm_pick_node.cpp:309`）和 `MovePath`（:662）的 MoveIt 用法抽出来、去掉硬编码。`pick()` / `place()` 仍留在接口里给以后的抓放任务用。

---

## D6. 对外默认坐标系 `base_link`

**结论**：目标位姿默认在 `base_link` 下描述，`frame` 参数可显式指定 `world`。

**理由**
- `base_link`（底盘）**不随升降柱移动**；`link_base`（机械臂底座）会随升降柱上下动 0~600mm，同一个坐标在不同升降高度下指向不同空间位置，不能当对外接口
- `base_link` 由 `robot_state_publisher` 从 URDF 树发布，**只跑机械臂 bringup 也存在**
- `world` 只由导航栈产生（`start/agilexpro/param/amcl_params.yaml` 里 `global_frame_id: "world"`），机械臂任务用它等于加一个"必须先开导航"的隐藏依赖

**放弃的方案**：默认 `link_base`（现有 `agx_xarm_pick` 的做法）——它随升降动，是坑

**影响**：`link_base` 只出现在实现内部，不出现在任务 YAML 里。

---

## D7. 任务串行，一次一个

**结论**：同一时刻只跑一个任务，忙时拒绝新请求。

**理由**：硬件只有一台。两个任务同时指挥机械臂/升降柱会打架。

**影响**：Runner 用 mutex + busy 标志；不需要任务优先级、队列。

---

## D8. 参数 = YAML 默认 + 请求可覆盖

**结论**：默认值写在任务包 `config/<task>.yaml`；action goal 里的 `params_yaml` 可覆盖。

**理由**：以后如果有上位机/调度器统一派活，它必须能带参数下发（同一个任务，这次抬 100mm、下次抬 300mm），否则每次都要改文件重启。

**实现**：Runner 用 yaml-cpp（系统已装 0.6.2）解析 `params_yaml`，写进 `/agx_task/<task_name>/`，然后才调 `configure()`。任务代码只读 `pnh()`。

**放弃的方案**：只从 YAML（简单，但接调度器时要返工）

---

## D9. 危险操作不加 `confirm` 参数

**结论**：`LiftCapability::home()`（会真实下降到下限位）这类操作不要求调用方传 `confirm=true`，而是**单独分组**（放在接口的"危险"区段）+ 文档说明。

**理由**：`confirm=true` 是形式主义——写着烦，真出问题时拦不住。分组 + 命名 + 文档能起到同样的提示作用。

**放弃的方案**：`home(bool confirm)`（防手滑，但啰嗦）

---

## D10. 升降柱：改模型让 MoveIt 感知，不自己写运动学解算

**结论**：在 URDF 里插入升降棱柱关节，让 MoveIt 的模型跟着实际高度变；**不写自定义运动学解算**。

**理由**（这条是本次讨论最重要的取舍）

| | 自己写解算 | 改模型 |
|---|---|---|
| 工作量 | 几周 | 半天 |
| IK | 要自己写（xArm6 是偏置腕，解析解麻烦） | 用现成的，本来就对 |
| 碰撞检查 | 要自己写或没有 | 自动正确 |
| 轨迹/速度规划 | 要自己写 | 自动正确 |
| 出错后果 | 真机撞底盘 | 规划失败，安全 |
| 影响范围 | 只有这个任务，另起一套运动栈 | 全工作空间受益（含 pick demo） |

关键认识：**升降柱不是运动学问题，是模型问题**。
- 机械臂自身的 IK 不受升降影响（升降只是把机械臂整体平移）
- 真正坏掉的是**碰撞检查**和 `base_link`/`world` 到 `link_base` 的换算
- 重写解算解决不了碰撞检查，反而会丢掉它

**实测确认的现状**（2026-09-24）
- 实际加载的模型是 `ranger_xarm6_lifting_2431.xacro`（`planning_context.launch` 第 22 行被第 44 行覆盖，后写生效）
- 它 include 的是 `ranger_xarm_base/urdf/ranger_xarm_2431.xacro`，里面**没有升降关节**，升降被建模成一个死的固定偏移：
  `box_link --ranger_with_xarm (fixed, xyz=(-0.17, 0, 0.555))--> arm_base --world_joint (fixed)--> link_base`
- 所以改法不是"把 fixed 改成 prismatic"，而是**插入新关节**：
  `box_link --(fixed)--> lift_column_link --(prismatic 0~0.6, axis z)--> arm_base`
- MoveIt 的关节状态源里也没有升降（`realMove_exec.launch:63` 只喂 `xarm/joint_states` 和 `gripper_slider/joint_states`）

**放弃的方案**
- 自己写考虑升降的运动学解算
- 任务层做 Z 换算 + 强制升降在某高度（只修 IK，碰撞检查仍然是错的）

## D11. 升降柱不做锁，用 `waitSettled()`

**结论**：任务开头调 `lift().waitSettled()` + `isInRange()`，不做占用锁。

**理由**：上层是串行安排的（另一个任务负责升降，它结束本任务才开始），不存在并发争抢。

**但必须检查"停稳"**：升降服务是**非阻塞**的（`1_lifting_motor_config.json` 里 `"callBackMode": 1` → `SververCallbackImmediately`），另一个任务很可能"发完指令就返回了"，物理上还在动。

**放弃的方案**：任务间升降柱占用锁/租约（过度设计）

## D12. TCP 取"指尖下沿"，取值为**实测值**

> **状态更新（2026-09-29）**：闭合值经复测确认为 **0.170 m**（初测 0.230 m 作废，见 D16）。
> 下表已按复测值更新；张开值未复测。

**结论**：`tcp_link` 定义在 `link6` 正下方 `z = 0.170`，即**夹爪闭合状态下两指尖下沿的中点**。

**取值来源**：**实机测量**（卷尺/卡尺，法兰安装面 → 指尖最低点），2026-09-29 复测确认

| 夹爪状态 | 实测 | 模型 FK 算得 | 差值 |
|---|---|---|---|
| 闭合（finger=0.6524） | **0.170 m** | 0.147 m | +0.023 m（网格略短，方向保守） |
| 张开（finger=0） | ⏸ 未复测（旧记 0.220 m 作废） | 0.132 m | — |

**为什么优先信实测**：模型算的是夹爪四个连杆的 FK（指节是 mimic 关节，可以精确计算）。
初测曾出现 60 mm 级别的偏差，**错的是实测值（参照面理解不一致）而不是模型**（见 D16）。
任务执行时的位姿精度直接取决于这个数，用错的数会让指尖悬空或扎进放置面。

**注意**：张开/闭合差 10mm。示教和执行时**夹爪必须保持同一状态**（建议都闭合）。

**放弃的方案**
- 夹持中心（两指中间，适合"夹着物体去放"；但本任务不夹东西）
- 直接用模型算的 0.147（比实测 0.170 短 23mm，会让指尖少走 23mm —— 偏差量级可接受，
  但既然已有实测值就没理由用模型值）

**影响**：任务 YAML 里不需要这个数（它在 URDF 里），但**示教读位姿必须用 `tcp_link`**，否则换算会引入误差。

## D16. 夹爪模型比实物短约 83mm（✅ 推断作废，2026-09-29）

> **状态更新（2026-09-28）**：用户复核认为"短 83mm"存疑，需重新测量。
> **状态更新（2026-09-29）**：复测完成——**这条推断是错的**。实测闭合 0.170 m vs 模型 FK 0.147 m，
> 只差 **23 mm**。真正错的是**实测值本身**（0.230 → 0.170，参照面理解不一致），
> 已据此修正 `tcp_joint`（见 D12）。复测记录见 `measurements.md` 的 M2。

**原结论（已作废）**：曾认为 URDF 里的夹爪沿工具轴方向比实物短约 0.083 m，碰撞体因此偏短。

**证据（已修正）**
- 实机测量：法兰安装面 → 指尖 = **0.170 m**（闭合，2026-09-29 复测；初测 0.230 m 作废）
- 模型 FK（含夹爪基座网格）：法兰 → 最低点 = 0.147 m（闭合）
- 实际差值 = 0.023 m，方向是**网格略短**（碰撞体偏保守）
- 夹爪基座网格 `base_link.STL` 自身尺寸：67 × 93 × 138 mm（z 方向 138mm）
- 模型里 `link6` → 夹爪基座的关节 `xarm_with_ag95` 是恒等变换（`xyz="0 0 0"`），即**没有建模任何转接件**

**可能的成因**（未确认，需现场核对）
1. 法兰与夹爪之间实际装了转接件，URDF 里没建
2. 实物夹爪不是模型对应的那个型号/版本（驱动配置写的是 `AG95_MB`）
3. 模型网格本身的尺寸不准

**影响**
- 不影响"移动到指定位姿"的精度（`tcp_link` 用的是实测值）
- **影响碰撞检查**（若结论成立）：本任务要往底盘附近放东西，而 MoveIt 认为夹爪比实际短 83mm，**可能规划出实际会撞的路径**。这是目前唯一的实质安全缺口。（⏸ 该 83mm 本身存疑，见本条顶部状态更新）
- 也影响 `agx_xarm_pick`（它一直用这个模型）

**后续选项**
1. 在 URDF 里把 `xarm_with_ag95` 的 origin 改成实测的转接长度，让模型和实物对齐（一行改动，但会让 RViz 里夹爪位置看起来"离法兰更远"，与实物一致）
2. 核对实物夹爪型号，换用正确的网格
3. 暂不处理，但**任务执行时避开底盘附近**（保守做法）

**状态**：⏸ 2026-09-28 复核存疑，待重新测量（见本条顶部状态更新与 `measurements.md` M2 复测方案）

## D13. 目标平面用示教确定，不用模型推算

**结论**：把机械臂拖到目标位置，读 TF 得到位姿，写进任务 YAML。

**理由**：模型不可信，至少三个来源——悬架/轮胎压缩、装配公差、那个 0.555 的升降偏移本身就没验证过。**示教和执行用同一个模型，模型误差自动抵消**（只要两次升降柱高度一致，这正是 `lift_min_mm`/`lift_max_mm` 要卡的）。

**放弃的方案**：用模型算出"底盘平面离地 0.32m"再换算成 `base_link` 坐标——模型值只能当参考，不能当依据

**影响**：见 `measurements.md` 的示教表格；建议教 2~3 个 x/y 位置以验证"平面平行于底盘"这个假设。

## D14. 升降桥接节点放 `agx_xarm_bringup`，不放 `tasks`

**结论**：`lift_joint_bridge.py` 放 `src/start/agx_xarm_bringup/scripts/`，由 `setup_arm.launch` 启动。

**理由**：它是"让机器人模型变对"的 bringup 工作，和现有的 `gripper_traj_bridge.py` 同类；而且修好之后 pick demo、RViz、控制台都受益，不只服务任务层。

**影响**：任务层不需要知道桥接节点的存在，只管用。

## D15. 修改现有 URDF 的风险已知

**结论**：接受"改 URDF 会影响现有东西"的风险。

**影响面**：`lifting_joint` 变成可动后，RViz、控制台、pick demo 的碰撞检查都会跟着变。升降柱升起时，pick demo 那些硬编码的 HOME 位姿可能开始报规划失败——这是**模型变对了**的正常现象，但需要回归验证一遍。

**回归清单**：`setup_arm.launch` 启动 → RViz 里机械臂高度是否跟着升降动 → 控制台滑条是否正常 → pick demo 在升降 0 时是否还能跑通。

## D17. 新增静态参考系 `link_base_lift0`（lift=0 快照），launch 做、不进 URDF

**结论**：在 `setup_arm.launch` 里用 `static_transform_publisher` 发布 `base_link → link_base_lift0 = (-0.19, 0, 0.555)`（rpy=0）。`link_base_lift0` 恒为 lift=0 时机械臂底座的位姿快照；运动的 `link_base` 保持不变（仍挂 prismatic `lift_joint`）。

**理由**
- `link_base` 随升降动（这是 D10 高度感知机制的根基，**不能动它**），但上层需要一个固定参考来描述"机械臂底座在底盘上的安装位"（如：相对底座的工作区、离底座固定距离的点位——这些量天然在 lift=0 参考系下）
- 数值直接来自 lift_joint 定义：z=0.555（lift=0 时底座高度，M1 实测 875=320+555 一致）；x=-0.17(lift_joint origin) - 0.02(ranger_with_box) = -0.19

| 方案 | 改动 | 为什么选/不选 |
|---|---|---|
| A：launch 静态 TF（**采用**） | `setup_arm.launch` +3 行 | 不碰 URDF/MoveIt，重启 launch 生效；A/B 输出无差别 |
| B：URDF 加 fixed joint + 零几何 link | 改 `ranger_xarm6_lifting_2431.xacro` | 新 link 会进 MoveIt 机器人模型，牵动配置与回归，收益无差 |

**实测验证**（2026-09-28）：`tf_echo` 显示 `link_base_lift0` 恒 (-0.190, 0, 0.555)；lift=0 时与 `link_base` 重合到差 1mm（URDF 标称 0.555 vs 编码器实测 0.556，M1 已含此差）；**lift=300 分离验证已做**——`link_base` z=0.855（=0.555+0.300 严格吻合）、lift0 保持 0.555 不变，旋转恒等。**方案 A 全项验证通过。**

**影响**
- 与 D6 不冲突：对外接口仍默认 `base_link`；`link_base_lift0` 供实现内部固定参考，运动/固定两帧按需取用
- `lift_zone_viz.py` 绿盒继续挂运动的 `link_base`，未动

## D18. 新增 `deck_top`：2431 箱体顶面（升降柱安装平台）静态参考系

**结论**：在 `setup_arm.launch` 里用 `static_transform_publisher` 发布 `link_base_lift0 → deck_top = (0, 0, -0.208)`（rpy=0，链在 D17 之下）。`deck_top` 标定 2431 箱体顶面在 `base_link` 系 (-0.19, 0, 0.347)，离地约 667mm——它是**升降柱所在的安装平台面**，可作为"底盘上层平台 xy 平面"的参考。

**来源**
- **208mm = 卡尺实测**（用户 2026-09-28）：lift=0 时臂底座底面 → 箱体顶面的间隙；与 M1 网格分析目测值一致
- 推导自 D17 链：lift0 的 z=0.555 − 0.208 = **0.347**

**为什么不是"绿盒底部 650/645mm"**（讨论中推导过、记录在此防止重犯）
- 绿盒全长 650mm 是包围盒尺寸，其中心在 link_base 系 z=−0.320、半高 0.325 → 底部在 **−0.645**（5mm 是顶部陷入法兰的余量，不在下方）
- 绿盒挂在**运动的** `link_base` 上，整个盒子随升降走；lift=0 时其底面在离地 225mm——**处于 Ranger 底盘顶板（离地 320mm）之内**，只是"盖住柱子的包围盒"下沿，与任何物理表面都不对应
- 需要静止的底盘平台参考 → 必须挂在 lift0 链上，不能用柱体包络反推

## D20. 升降坐标系断电会丢：`initMode=0` 的旧认知是错的，改为「上电校验 + 未标定拒绝位置指令」

**背景（2026-09-29 实测确认）**：在 lift 高度非 0 时整机电断电，重启后节点把高度当成 0。抓当时的状态：

```
backPos: -206        → backHeight: 0      # 驱动 0xE0 位置寄存器原值，软件不做换算
initState: True      → 控制台显示「已到达 0mm」
downLimit: False                               # 下限位开关没被压到 → 柱子物理上不在最低点
```

**根因**：830ABS 的位置基准是靠「下降压下限位 + 清零（0x4B/0x4C）」建立的，**整机断电重启后这个基准会丢失**，驱动器多圈位置回到 ≈0。而 `1_lifting_motor_config.json` 里 `initMode=0` 关掉了开机自动初始化，于是节点拿着一份失真的原点开机。

- `AGENTS.md` 原先写的「绝对值编码器，`initState` 会保留，正常情况下无需重新初始化」**不成立**。`initState` 只是节点自己的软件标志（`mode != 1` 就置 True），和驱动器位置基准是否还在毫无关系。
- 驱动自己的 README 其实写对了：`initMode` 「1=上电开始初始化，**建议测试好功能后…再去改为 1**」；`MotorClearPosZero()` 的注释也写着「这个指令**失电失效**，每次上电初始化都会执行」。

**为什么这件事严重**（不只是"显示不对"）
1. `lift_joint_bridge.py` 把假 0 喂给 MoveIt 的 `lift_joint` → TF 和碰撞检查全错，且无任何告警
2. 控制台显示「已到达 0mm」+ `initState: True`，给人假安全感
3. **最危险**：`lift 600` 会让物理柱子从当前位置**再往上走 600mm** 撞机械硬限位；软件侧 `back_lift_height >= upLimitVal` 保护读数是 0，拦不住
4. 附带发现 `lifting_motor_ctrl.py:MotorStop()` 里 `elif upLimit: SetStopFlag(True)` 会被紧随其后的 `if back_lift_height >= 上限 ... else SetStopFlag(False)` **无条件覆盖**，机械限位开关在方向判断分支里实际从未生效

**结论**
- **C（治本）走不通**：查证后确认 `830ABS` 驱动器（Modbus 从站，寄存器 0x00/0x02/0x09/0x10/0x1C/0x1D/0x4A/0x4B/0x4C/0x4D/0x51/0x53/0x58/0xE0）**没有"掉电保存位置"这类寄存器**，本机也没装 WinEDS。行业通行做法是电池/电容维持多圈计数（`A.81/A.83 绝对值编码器备份/电池组错误`），长时间断电照样丢。→ **每次上电后 `lift init` 是唯一可信的恢复手段**
- **不用软清零代替**：把当前位置当 0（`LiftTimeoutInit`）虽然自洽，但 0~600mm 就不再对应真实机械行程，`lift 600` 可能顶穿上限。只能下降到下限位开关重新建零。
- **不加 `initMode=1` 自动初始化**：`initMode=1` 会在**每次开机时无人值守地自动下降**，而且驱动在超时/过载时会走 `LiftTimeoutInit` 在当前位置软清零，把"下限位坏了"这个硬件故障悄悄变成一个看似正常的任意零点。安全上应该由人显式执行。
- **改为「上电校验 + 未标定就锁死」**：节点把可信高度落盘到 `~/.ros/lift_frame_m<id>.json`；上电时和驱动器读数比对，差 > 容差（默认 20mm）就判定坐标系不可信 →
  - `initState=False` → 下游**零改动**自动降级（`lift_joint_bridge` 保持上次高度、控制台置灰）
    - 实现上必须**独立**于上游的 `init_state`：上游各 mode 分支的 `and self.init_state` 判据依赖它，
      兼用会导致坐标系一不可信，连**急停(-2)**都被拒。只在发布 `initState` 时合成
      `self.init_state and self.frame_valid` 给下游看
  - 50Hz 定位回路改为 force 急停，**不下发任何位移**
  - 服务端拒绝位置模式(`mode=0`)和**所有**速度模式(`-4`/`-7`，**含下行**)，返回 `-14`
  - 放行 `mode=1` 初始化 / `-2` 急停 / `-3` 清故障 / `-6` 清零
  - 初始化跑完 = 坐标系重建，重新开放并立刻落盘
- **同时修 `MotorStop()` 限位保护**：改成"该方向上确实没碰到任何限位时才置 False"。这条是最后一道机械兜底——即使坐标系统一错了，限位开关也能真的把柱子停在行程内。

**改动落在第三方包的理由**（AGENTS.md 要求说明）：门禁必须在**驱动 50Hz 定位回路**那一层才拦得住，跨节点的旁路节点挡不住它自己下发位移，所以必须改 `lifting_ws/src/lifting_ctrl/`（AgileX 上游包），所有改动以 `[agx-fix 2026-09-29]` 标注，未动协议/寄存器/线程模型。

**参数**（不重编译即可调）
| 位置 | 参数 | 默认 | 说明 |
|---|---|---|---|
| `lifting_ctrl` 节点 | `~frame_check` | `true` | 关掉=不比对直接信任驱动器（不推荐，只是绕过） |
| `lifting_ctrl` 节点 | `~frame_tolerance` | `20` mm | 上电比对容差 |
| `lifting_ctrl` 节点 | `~frame_file` | `~/.ros/lift_frame_m<id>.json` | 基准高度落盘位置 |
| `lift_joint_bridge` 节点 | `~state_file` | `~/.ros/lift_last_height.json` | MoveIt 回放用的上次高度 |

**已知不足**
- 回放给 MoveIt 的"上次高度"是**停机时**的值，不等于开机瞬间的真实高度（柱子是丝杠自锁的，不会自己走，所以这个近似成立）
- `LiftTimeoutInit`（超时/过载初始化）落到的 `0xF2` 分支我判定为**放行**（坐标系自洽）+ `logerr` 强提醒：此时 0~600 不再对应真实行程，靠修好的限位开关兜底。要更保守可以改成也拒绝
- **⚠ 速度模式不能靠限位开关兜底（2026-09-29 实测证伪）**：原设计放行了 `mode=-4` 的**下行**，
  理由是「下行有下限位开关兜底」。真机测试直接证伪：`ModeCtrl` 的 `-4` 分支**每拍无条件**
  重发 `LiftMoveSpd`，**没有到位/超时退出条件**，一条 `mode=-4 val=-20` 让柱子从 0 一路降到
  **-141mm**（高度读数为负，说明软件行程下限也没拦住），只能靠人工急停掐住。
  速度模式和位置模式一样是「会一直跑到撞限位」的指令，未标定时一律拒绝。
- **离线测试**：`src/tasks/tests/`（`run_all.sh` 一次跑全，共 58 断言）。不碰串口、不碰真机、
  不需要 roscore、落盘走临时目录，**可以在机器人运行时安全执行**。改门禁逻辑后请重跑。
- 判定不了"仅重启电脑、驱动器没断电"的情况——那种情况位置其实还在，但因为本机没做过基准落盘，第一次会走"无历史记录 → 暂信"分支

## D21. 夹取做成「一个原子服务」而不是控制台点两次；到位判据用「位置不再变化」

**背景（2026-09-30）**：需求是"夹爪移动到红球处后夹取，以后做自动化流程，现在先在 UI 控制台加夹取按钮，
夹爪闭合参数可输入调节以夹不同大小物品"。

**结论**
1. 夹取 = `plane_target/grasp`（`std_srvs/Trigger`），在 `agx_plane_target` 节点里**一次完成**
   「(可选)张开 → MoveIt 移到红点 → 闭合到目标值 → 回报实际读数」。控制台只发一条服务调用。
2. 闭合参数走**参数服务器**（`~grasp_position` 等，每次夹取重读），控制台点按钮前先
   `nh_.setParam(...)` 再调服务。
3. 进度反馈走 `plane_target/grasp_status`（`std_msgs/String`，格式 `"<state>|<text>"`，latched）。
4. 到位判据 = **位置读数连续 N 次不再变化**，不读 `grip_state`。
5. 急停（`plane_target/stop`）能中断闭合阶段，方式是**重发当前位置**（保持）。

**理由**

**(1) 为什么要做成一个服务，而不是控制台点两次**
- 用户明确说"以后会实现自动化流程"。**自动化的原子单位必须是服务**，不能是"人点两个按钮"。
  做成一个服务后，状态机/脚本 `rosservice call /plane_target/grasp` 一次就够，将来 `agx_xarm_smach`
  直接复用，不需要再改任务层。
- **互斥安全**：`self.busy` 在整个序列（移动 + 闭合）期间保持为真。控制台、RViz 短按、`home` 都走
  同一个 `xarm6` 控制器，如果拆成两个独立动作，"移动完了但还没闭合"的窗口里插进一个 GO，
  就会在**半闭合**状态下被抬走——这是最容易出事的场景。
- 放弃的方案：控制台点「GO」再点「夹爪闭合」。缺点是每次两点、且没有互斥保护；优点是能分开调试。
  折中办法是 `~grasp_preopen` + 独立的 `/plane_target/go` 都保留，调试时仍可分开用。

**(2) 为什么参数走 param 而不是自定义 srv**
- 和已有的 `~rpy_deg` 同一个套路（每次 GO 重读，`rosparam set` 就能调），控制台不需要新的消息依赖。
- 换物品尺寸只改一个数字、不重启任何节点——这正是"夹取不同大小物品"的实际需求。
- 放弃的方案：自定义 srv 带 `position` 字段。语义更干净，但要多一个 `.srv` 文件 +
  `agx_plane_target` 就要依赖新消息包，而收益只有"少一次 setParam"。**接口契约的正式化留给
  `agx_task_msgs`**（`interface.md` 冻结版里已有位置），等真上状态机时再一次性对齐。

**(3) 为什么状态用 `std_msgs/String` 而不是结构化消息**
- 分层硬规则：`start` 禁止依赖 `tasks`。自定义消息要么让 `start` 依赖 `tasks` 的 msg 包（违规），
  要么再加一个中立 msg 包（此时才值得）。
- 状态只有三态 + 一句话，`Trigger` 的 `message` 字段本来就是这个用法（现有代码已在用）。
  格式 `"<state>|<text>"` 有明确文档，解析只切第一个 `|`（`test_grasp.py` 有断言守着）。
- 放弃的方案：`moveit_msgs` 之类。语义不符，且为一个三态进度引入重依赖不划算。

**(4) 为什么到位不看 `grip_state`**
- `grip_state` 的 0/1/2 语义**从来没实测过**（`measurements.md` M4 至今是空表）。`agx_xarm_pick`
  里的 `waitGrasp` 也没人验证过。现在猜它等于**把猜测写进安全相关的判断**。
- "位置不再变化"是**能观测的事实**：AG95 到位后位置读数稳定，夹到东西停在物体宽度上，
  空夹到底停在 0。三种情况都能被"停住 + 停在哪"如实描述，**不需要知道厂商枚举的含义**。
- 代价：到位判定有 `~grasp_settle_timeout`（默认 3s）兜底，超时会**明确报出实际停在多少**而不是谎报成功。
- 起步窗口（0.25s）不可省：指令刚发出时手指还没动，那段"静止"是假的，不加窗口会立刻误判到位
  （`test_grasp.py` 第 3 项专门用"延迟 0.3s 才动"的假设备守着这条）。

**改动落在哪**
- `src/tasks/agx_plane_target/scripts/plane_target_marker.py`：新增 grasp 服务 + 夹爪读写 +
  把 `_motion` 拆成 `_execute_motion`（不管 busy）+ `_motion`（管 busy）。**这个拆分是必需的**：
  原来的 `_motion` 在 `finally` 里无条件清 `busy`，夹取会在"移动完、还没闭合"时把控制器让出去。
- `src/start/agx_xarm_bringup/src/joint_slider_panel.*`：控制台加一行「夹取」（`QSpinBox` 闭合位置 +
  按钮 + 状态标签）。依赖方向仍是 `start` → 松耦合字符串接口，没引入对 `tasks` 的编译依赖。

**安全约束**
- `enable_arm=false`（干跑）时**只规划，绝不闭合夹爪**。干跑的语义是"不碰真机"，闭合也是碰真机。
  有专门断言守着（`test_grasp.py` 第 7 项 + 隔离 roscore 下 fake AG95 收到 0 条指令）。
- 干跑路径**先播 `busy` 再播 `ok`**：否则控制台按钮会一直亮到流程结束。
- 失败时**不闪绿**：`ok` 只在真的夹完（或干跑明确说明）时发，其余一律 `fail` 并闪橙。

**已知不足**
- **不判断"夹住了还是夹空了"**：只报实际停住位置，操作者自己看（停在目标值 = 大概率空夹，
  停在比目标大 = 大概率夹到东西）。要做可靠判断得先补 M4 实测。
- `~grasp_force` 固定 50（和夹爪滑条一直发的一致），没在 UI 暴露——用户只要了闭合位置。
  要调就 `rosparam set /plane_target_marker/grasp_force 30`，已在参数里留好。
- 到位判定是"位置稳定"，对**极轻物体被夹飞**这种情况无能为力（位置会继续变→超时→如实报失败）。
- 张开那一步也走同一套"等稳定"，所以**里面还夹着东西时张开可能超时**（报 fail，不强行动作）。

**验证**
- 离线：`src/tasks/tests/test_grasp.py`（11 组，含到位判定/起步窗口/急停中断/超时/干跑不闭合/
  度弧度回归），已并入 `run_all.sh`（不碰串口、不碰真机、不需要 roscore）。
- 隔离 roscore（11399）+ fake AG95：验证跨进程接口契约、真实路径的夹爪阶段、
  MoveIt 缺失时如实报失败且**不下发闭合指令**。
- ⏸ **真机端到端未做**：需要人工清场 + 物理急停在手边。

4. 六个点在 RViz 里是**纯展示** MarkerArray（`plane_target/put_points`，ns `put_points`，
   id = 点号、id 100+n 是编号文字，坐标系 `link_base_lift0`），不是 interactive marker。
5. 直线两段（下降/抬高）用 `compute_cartesian_path` + 客户端重定时，**明确清掉**黄区路径约束；
   另两段（到上方点 / 回 initial）照常带黄区约束，并**把约束盒底面抬到放入点高度**
   （实现"不得降回放入高度"）。
6. 终端接口 = `scripts/put`（`put <1~6>` / `putN` / `put status` / `put stop` / `put install`；
   脚本自己补 ROS 环境，用法对齐 `~/bin/lift`）。

**理由**

**(1) 为什么点号必须在服务请求里，而不是 param + Trigger**
- 一次 `put 3` 必须是一条**不可分割**的指令。先 `rosparam set` 再调 `std_srvs/Trigger` 会留下
  "点号已改、服务还没调"的窗口，其间任何别的动作都能插进来；而且服务响应里看不到用户请求的
  是哪个点，出事故无法复盘。
- 放弃的方案：`Trigger` + 参数（省一个 .srv 文件）；只给 `rosservice call` 用原生服务名
  （省掉 CLI，但操作者要背服务名和字段名，且没有进度显示）。

**(2) 为什么进度不复用 `grasp_status`**
- 控制台「夹取」行订阅 `grasp_status`：把 put 进度灌进去，会让「夹取」行显示"放入完成"并按
  ok/fail 逻辑重新同步夹爪滑条——**这就是"和原来的控制台冲突"**。
- 需求方明确说"新的发布不要和原来的控制台冲突"，所以 put 对外一律用新名字
  （`put_status` / `put_points`）；控制台一行代码没改，`busy` 互斥天然隔开两个功能
  （put 期间点「夹取」/「GO」都被服务拒绝）。

**(3) 为什么红球是纯 Marker，不是可拖动 marker**
- 六个点是**示教定值**（M6），不是每次任务现场拖的；做成可拖动会多一个"被拖歪"的不确定源，
  还要和红点抢同一个 `InteractiveMarkerServer` 的拾取（WORKLOG 坑 13）。
- 编号文字 + `put install` 让"命令行点号"与"RViz 里的球"对得上号。
- 放弃的方案：复用红点那种交互 marker 做"拖动重示教"——留给以后的示教模式。

**(4) 为什么竖直两段走 Cartesian、且不套黄区约束**
- 放入是"压着物体放"，下降必须是直线，不能自由规划出扫掠（计划原文：必须是直线运动）。
  `compute_cartesian_path` 保证直线；`avoid_collisions` 默认 True，**碰撞检查保留**。
- 六个点是示教值，**可能在黄盒外**；给直线段套 `PositionConstraint` 会让规划直接失败。
  所以竖直两段 `clear_path_constraints()`（`test_put.py` 有断言守着）。
- 另两段仍是普通规划：照旧带黄区约束，另外把约束盒**底面抬到放入点高度**（"不回到放入
  高度以下"）；目标点落在黄盒外时按既有"起点在区外"的先例**最小化扩盒**并 `logwarn`。
- ⚠ `compute_cartesian_path` 的服务端**总是按 100% 速度**做时间参数化（Noetic 的
  CartesianPath capability 固定 `computeTimeStamps(rt, 1.0)`，忽略 `~vel_scaling`），
  下降会"蹬"下去；所以执行前在客户端用 `retime_trajectory(..., ~vel_scaling, ...)`
  重定时（同一算法、客户端实现），失败时退回原轨迹并 `logwarn`（偏快，已明说）。

**(5) 为什么点号 1~6 = M6 表格顺序，坐标写在节点常量里**
- 表格顺序就是示教记录顺序，便于对账；坐标在 `plane_target_marker.py` 的 `PUT_POINTS` 常量，
  `measurements.md` M6 是记录来源，`test_put.py` 用硬编码 M6 数值守住两边不漂移。
- 与黄盒不同，这些坐标没有第二个消费者（没有别的包要读），所以不引入 param 服务器接口。

**安全约束**
- `enable_arm=false`（干跑）只规划 `1/5 移动到上方点`，并明确报告"下降/松开/抬高/回家未执行"；
  不移动、不松开（有断言）。
- 失败/急停一律报 `fail` 并说明**停在哪、物体是否还夹着**；松开失败**不抬高、不回家**。
- 整个放入期间 `self.busy` 占用；`/plane_target/stop` 可打断（手臂停住、夹爪保持当前开合）。

**已知不足**
- 干跑只验证第 1 步：不动机械臂就无法从"假设的上方点"继续规划直线段，所以第 2~5 步在干跑里
  是**明说跳过**，不是假装规划过。
- 到位判据沿用夹取的"位置停止变化"（不读 `grip_state`，M4 仍未实测）。
- 放入点在 `link_base_lift0` 里示教；升降高度不同靠 TF 换算（同 一个世界坐标）。高度差太大
  够不着时规划会失败并如实报出（不会去够）。
- ⏸ 真机端到端未做：需要清场、物理急停在手边、以及一个真实物体。
- ⚠ 操作面：put 期间按控制台「回到初始位置」不会插进手臂动作（`busy` 会拒绝），但该按钮**按下时先发
  一条夹爪张开指令**（`goToInitialPose()` 里的 `sendGripper()`），会把物体松开——现场须知说明。
  夹爪滑条同理：手动夹爪控制一直在线，`busy` 拦不住，属既有设计。
